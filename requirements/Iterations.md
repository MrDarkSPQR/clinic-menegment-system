# План ітеративної розробки системи Clinic Management System

Проєкт розбито на три послідовні етапи, що дозволяє швидко перевіряти робочі прототипи та вчасно знаходити технічні проблеми.

---

## Порядок розробки

1. Базовий бекенд та архітектура даних
2. Веб-сайт для пацієнтів та форма онлайн-запису
3. Локальний десктопний додаток, синхронізація та перевірка тріалу

---

## Опис етапів

### Ітерація 1: Базовий бекенд
*   **Мета:** Налаштувати сервер і підготувати таблиці бази даних для роботи з пацієнтами.
*   **Результат:** Готовий каркас сервера на FastAPI, описані моделі таблиць через SQLAlchemy та створені перші робочі запити (POST для додавання людей і GET для отримання списку).
*   **Ризики:** Помилки в структурі таблиць, які потім буде важко міняти. Для цього спочатку закладаємо гнучкі UUID замість звичайних порядкових чисел ID.

### Ітерація 2: Веб-сайт та онлайн-запис
*   **Мета:** Створити публічну сторінку, через яку люди зможуть залишати заявки на прийом.
*   **Результат:** Інтерфейс форми запису на React та TypeScript. Налаштовано Axios для відправки цих заявок на бекенд, де вони зберігаються зі статусом "Нова заявка".
*   **Ризики:** Пацієнти можуть вводити криві дані або слати спам. Для захисту треба буде додати валідацію номерів телефонів на фронтенді.

### Ітерація 3: Десктопний додаток та синхронізація
*   **Мета:** Зробити автономне робоче місце для клініки та зв'язати його з сайтом.
*   **Результат:** Графічний інтерфейс програми на PyQt6, який працює з локальним файлом SQLite без інтернету. Написано логіку синхронізації, яка стягує нові записи з сервера та переносить локальні зміни лікаря в хмару. Додано блок перевірки 3-денного тестового періоду програми.
*   **Ризики:** Конфлікти в базі даних, якщо одну й ту саму годину займуть одночасно на сайті і в клініці. Проблема вирішується перевіркою міток часу при кожному обміні даними.
